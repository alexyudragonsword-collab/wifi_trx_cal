# 守卫有效性(当前真相)

## 形成背景

本项目的正确性主要不是靠人读代码维持的,而是靠守卫:分层守卫、调用面守卫、
金标对拍、端上条数断言、闭环重放、文档与原理图陈旧检查。既然结论都压在守卫
身上,**守卫本身出错就是最高等级的缺陷**——它不会让测试变红,它让"绿"或"红"
这两个字失去含义。

到 0.7.26 为止,本项目已经踩中守卫失效的**全部四种形态**,其中两种是在 2026-09
的工程体检与合并前复核中才发现的,分别潜伏了八天和三周。AGENTS.md 原有的规则
"写完守卫必须用变异确认它真的会红"只覆盖其中两种;本文记录另外两种长什么样。

## 当前结论:四种失效,以及它们在 CI 上的样子

| 失效类型 | 守卫出了什么错 | 在 CI 上看起来 | 靠什么抓 |
|---|---|---|---|
| **空转** | 什么也没断言到 | 恒绿 | 变异 → 必须红 |
| **错靶** | 匹配到名字或注释,不是干活的那一行 | 恒绿 | 在**调用点**变异 → 必须红 |
| **恒红** | 前提在任何提交上都不成立 | 恒红 | 还原 → **必须绿** |
| **被遮** | 守卫本身没错,但排在会失败的步骤后面 | 根本不出现 | 核对哪些步骤**真的执行过** |

**这张表的要点在第三行。** 变异验证对恒红的守卫照样"通过"——它确实会红,而且
是每次都红。一个恒红的守卫和一个严格的守卫,从变异实验的结论上看**一模一样**。
唯一能把它们分开的问题是反过来问的:*没毛病的时候,它会不会变绿?*

第四行则连红都不给。`set -e` 下,排在失败步骤之后的检查不会执行,也不会报告
自己没执行;它在日志里的样子和"不存在"完全相同。

## 双向验证规程(contains: procedure)

写完或改完一个守卫,按顺序做完这六步,缺一步都可能留下上表里的某一类:

1. **先确认变异真的注入成功**,再看结论。替换锚点跨行未匹配会让变异变成空
   操作,于是守卫"通过"其实什么都没证明(2026-08-24 实际踩到)。
2. **变异 → 必须红。**
3. **还原 → 必须绿。** 这一步是 0.7.26 之后补进来的;0.7.16 与 0.7.26 两次
   事故都只做了第 2 步。
4. **扫源码文本的守卫,要匹配那一行真正干活的代码**,不是名字、不是注释里的
   同名词句。
5. **归一化要覆盖整个不可复现面,不能只归一化其中一半**;而且**归一化器匹配
   不到目标时要报错,不能放行**——否则它会安静地拿错误的文本去比对。
6. **断言取精确值而非下限。** 下限挡不住"新加一条、旧的一条悄悄不跑"这种
   总数不变的漂移(端上条数断言即按此设计)。

流水线一侧还有两条:

7. **关键检查不要排在可能失败的步骤后面。** 便利性步骤(artifact 上传)标
   `continue-on-error`,或移到门禁之后。
8. **读"哪些步骤真的执行了",不要只读 job 的红绿**;并且**每一条 lane 都要
   有人看**——推送线有徽章,而 schedule 线没有,这正是它能红三周的原因。

## 案例台账(contains: experience)

**空转**

- `test_cal_deps.py` 的计划检查只断言"不抛错",`validate_order` 退化成空操作
  照样通过。0.7.23 补上反向断言:反转后的计划**必须**抛错。

**错靶**

- 0.7.5 的手机陷阱守卫初版用 `index("Python.start")` 找调用点,先匹配到的是
  作者写在上一行注释里的同名文字;删掉真正的调用,守卫照样绿。改为匹配真实
  调用行后才成立。
- 同一类连踩四次:`Python.start`、`annotation_typing=False`、
  `_drop_package_initializers`(见 `cairn/Android出货线.md`)。

**恒红**

- **0.7.16(红八天)**:自检要求金标差值**精确为 0**。GitHub 托管 runner 的
  CPU 型号不固定,CPU/BLAS 求和顺序读出 7.1e-15 dB;numpy/scipy 与本地同版,
  排除版本差异。被推翻的假设:"金标在生成它的同一套 numpy 上必然位级复现"
  ——只对同一台机器成立。修法:断言改 `<= 1e-9`(测的是比较逻辑,不是位级
  复现)。
- **0.7.26(红三周)**:文档陈旧检查比对"已提交的 HTML"与"当场重建的 HTML",
  只归一化 ISO 时间戳,**把 provenance 页脚里的 commit id 留在比对文本里**。
  一个文件不可能记录包含它自己的那个提交——已提交的副本生成于父提交(工作树
  dirty),重建盖的是 HEAD——所以它**在任何提交上都不可能绿**。修法
  `tools/docs_staleness.py` 整体去掉页脚,并在页脚不匹配时报错而非放行。

**被遮**

- **0.7.26**:原理图检查 `tools/build_assets.py --check` 排在上面那条陈旧检查
  之后,`set -e` 下**从未执行过**。现场核查:它本身是干净的(4 张图最新),
  所以没有真实漂移被漏掉——漏掉的是**发现漂移的能力**。
- **0.7.6 时期**:APK 上传撞 GitHub 账户级存储配额,而上传步骤排在模拟器之前,
  编译版**唯一的物理检查被跳过**,job 红的原因却是存储记账。修法:上传移到
  端上门禁之后并标 `continue-on-error`,保留期 14 → 7 天。

## 被推翻的判断(contains: lesson)

- 工程体检报告 P0-1 说"修掉金标断言后,覆盖率、文档陈旧、原理图三步就会真正
  执行"。**只对第一步成立。**后两步直到 0.7.26 才第一次跑起来——体检当时读的
  是 push lane 的结论,而这三步在 schedule lane 里。更正记录在
  `docs/backlog_zh.md` B26。
- "CI 绿"在 0.7.16 之前一直只指 `android.yml`;0.7.16 之后只指 `ci.yml` 的推送
  快线。**"CI 绿"始终是一个需要追问"哪条 lane"的说法。**
